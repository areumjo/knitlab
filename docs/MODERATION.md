# Maintainer guide: Explore submissions

This is your operating manual for reviewing and managing the public Explore gallery. The full backend design is in [`EXPLORE_BACKEND.md`](./EXPLORE_BACKEND.md); this doc focuses on the parts you do by hand.

## Daily flow: what happens when someone publishes

1. A user clicks **Share** in the editor, fills the form, clicks **Copy submission & open GitHub**, pastes the body, and submits.
2. GitHub creates an issue with the `design-submission` label. You get a notification.
3. You review it (see "How to review" below).
4. If good, you add the `approved` label. The Action runs (~30s), commits the design files + manifest update to `main`, deploys to Pages (~1 min), then closes the issue with a "Design published!" comment.
5. If bad, you remove the `design-submission` label or apply a `rejected` label and close the issue manually.

You don't need to merge anything by hand — the Action does the commit. Your only on-rails action is **applying the `approved` label**.

## How to review a submission

Open the issue. The body has these sections (auto-generated by the publish flow):

- `### Title` — what the user wants to call it
- `### Author` — display name (or empty if they want their GitHub handle used)
- `### Description` — optional context
- `### Tags` — comma-separated, lowercase
- `### Remix of` — empty unless this is a fork; if set, points to a previous design's ID
- `### Thumbnail` — base64 PNG inside a ` ```knitlab-thumbnail ` block
- `### Payload` — base64 `.knitlab` inside a ` ```knitlab-payload ` block

**You don't need to decode the payload manually.** The Action will validate it, write a comment if the format is broken, and refuse to publish. So your review is mostly editorial:

| Check | What to look for |
|---|---|
| Title | Reasonable, not spam, not offensive |
| Description | Coherent, relevant |
| Tags | Sensible categories, no slurs or promotional text |
| Submitter | Active GitHub account, not obviously a throwaway spam account |
| Thumbnail (visible inline if rendered) | Looks like a knitting chart, not unrelated/inappropriate imagery |
| Remix-of credit | If `Remix of` is filled, click through to the parent — confirm the fork actually changed something |

When in doubt, comment on the issue asking for clarification rather than rejecting silently.

## Labels and what they do

| Label | Effect |
|---|---|
| `design-submission` | Auto-applied by the publish flow. Tells the Action this issue is a candidate. |
| `approved` | **You apply this.** Triggers the Action → commit → deploy. |
| `rejected` | Convention only — has no automated effect. Apply when closing a bad submission so the reason is searchable later. |
| `needs-info` | Convention only — apply when you've commented asking for clarification and are waiting on the submitter. |

Only `design-submission` and `approved` matter to the Action. The rest are organizational hints for you.

## Common scenarios

### Submission has bad/missing data

The Action runs validation and posts a comment with the specific error (e.g., "Title is required" or "Thumbnail is not a valid PNG"). You don't need to do anything — the user fixes the issue body and you re-apply `approved`.

If they don't have permission to edit their own issue body (rare but possible), comment guiding them to open a new issue.

### Unchanged fork

If someone clicks **Open in Editor** on an existing design and immediately publishes without modifications, the publish flow shows them an amber warning ("This looks identical to the original — the maintainer will likely reject duplicate submissions"). They can ignore it and submit anyway. **You should reject these.** Comment "This appears to be an unchanged copy of #X — please make actual modifications before republishing" and close.

There's no server-side check yet, so this is your job for now.

### Remove a published design later

Someone reports a design as offensive, infringing, or just wrong, and you decide to remove it. Manual steps:

1. Edit `public/manifest.json` and delete the entry with the matching `id`.
2. Delete `public/designs/<id>.knitlab`.
3. Delete `public/thumbnails/<id>.png`.
4. Commit with a message like `Remove design #<id> per takedown request`.
5. Push to main → deploys automatically.

Optionally, lock the original GitHub issue and add a `removed` label so the conversation reflects what happened.

### Re-publish a design (corrections, updates)

Designs are immutable once published. To "update," ask the submitter to publish a new version (it'll get a new ID). If the change is significant, you can also remove the old one (steps above). For trivial typo fixes in the manifest, you can edit `manifest.json` directly and commit.

### Republished by someone else

If user B submits a design that's clearly a near-copy of user A's design, and B did not credit A in the `Remix of` field — comment asking B to add the attribution, or reject and ask them to use **Open in Editor** from the gallery (which auto-stamps the credit) instead of reuploading.

## Direct edits you might make to the manifest

You're free to edit `public/manifest.json` directly for things the Action doesn't handle:

- Fix a typo in a title or description
- Adjust tags after the fact
- Add a feature flag, sort hint, or curated-pick badge if we add such fields later

After committing, the next push to `main` deploys.

## Bypass: seeding demos without going through the issue flow

Use `scripts/seed-demos.js` to bulk-import legacy `.json` files from `/demo/` directly into the gallery. This is the path used to populate the initial Clawd demos. See the script's header comment for details. Re-running it overwrites entries with matching IDs.

## What's NOT automated

- Spam detection (you're the spam filter)
- License/copyright disputes (handle case-by-case)
- Editorial features (curating "Picks of the week," etc. — would require new manifest fields)
- Notifications when someone publishes (rely on GitHub's standard issue notifications)

If any of these become annoying, they're good candidates for follow-up automation.

## First-time end-to-end smoke test

Run this once after merging the Explore feature to `main` for the first time. It verifies the full publish → moderate → browse loop on the live site.

1. **Merge the feature branch to main.** (`git checkout main && git merge feature/github-backend && git push origin main`.) The Pages deploy fires automatically.
2. **Wait for deploy to complete** (~1 minute). Check the Actions tab on GitHub.
3. **Open the live site** at https://areumjo.github.io/knitlab/.
4. **Verify Explore loads.** Click the grid icon. You should see the 4 seeded Clawd demos. Click one — detail view opens, "Download .knitlab" works, "Open in Editor" loads it into the editor.
5. **Create a small test chart.** Just place a few stitches on a fresh canvas. Anything works.
6. **Publish it.** Click the share icon → fill title (e.g. "Test Submission") → Continue → Copy & open GitHub → paste body → Submit.
7. **Confirm the issue landed.** Check `github.com/areumjo/knitlab/issues` — your issue should be there with the `design-submission` label.
8. **Apply the `approved` label.** Within ~30s, the publish-design Action runs.
9. **Verify Action success.** Check the Actions tab. You should see:
   - "Process submission" — log shows "Published design #N: Test Submission"
   - "Commit and push" — commit lands on `main`
   - "Comment success and close issue" — bot comments and closes
10. **Wait for the second deploy** triggered by the bot's commit (~1 minute).
11. **Refresh the Explore page.** Your test design should now appear in the gallery.
12. **Click your test card.** Detail view shows correctly. "Download .knitlab" downloads. "Open in Editor" loads.
13. **(Optional) Clean up.** Edit `public/manifest.json` to remove the test entry, delete the test files, push.

If any step fails, the Action log will tell you why. Common gotchas: thumbnail format issues (reject as not-PNG), missing required fields (script comments back on the issue with the problem).
